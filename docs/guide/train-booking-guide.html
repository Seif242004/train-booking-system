0. How to read this guide, and the project on one page

The goal

A train booking system built as microservices for the e& internship program. A passenger searches trains, picks seats (the seats are held for 5 minutes), pays by card, and gets a PDF ticket with a QR code by email. An admin manages the timetable, supports passengers, books at the counter, and watches a live board of all trips.

How to run it

  1. Copy .env.example to .env and fill the values (never commit .env).
  2. docker compose --profile dev up -d --build starts everything (Oracle, Keycloak, OpenObserve, the five services, Gateway, web app, Mailpit, Stripe CLI).
  3. Open the web app on port 5173. The dev accounts and passwords are in your .env (names only: KEYCLOAK_DEV_USER_PASSWORD, KEYCLOAK_DEV_ADMIN_PASSWORD).
  4. node scripts/smoke-test.mjs runs a whole journey against the stack. node scripts/demo-data.mjs seed-demo fills the demo data.
  5. Tests: ./gradlew test (Spring services; they use throwaway Oracle schemas ending in _test) and cd gateway && npm test.

A sensible reading order

  1. docs/ARCHITECTURE.md (the flows) and chapter 1 of this guide.
  2. The Gateway (gateway/src/app.js): it shows every public route in one file.
  3. Train & Schedule: the simplest service (plain admin CRUD) and a good place to learn the Spring layers.
  4. Booking & Seat: the heart (availability, holds, the sweeper, confirmation, cancellation). Read availability/service/SegmentAvailability.java first, then booking/service/HoldService.java, ExpiryService.java, ConfirmationService.java, CancellationService.java, BookingIssueService.java.
  5. Payment, then Ticket and Notification (small services reached from Booking through the outbox).
  6. The frontend: frontend/src/App.tsx, then pages/SeatMapPage.tsx, pages/PaymentPage.tsx, pages/TripsBoard.tsx.

The rules to keep in mind everywhere

  • A journey from stop i to stop j uses segments i to j-1. A seat is available only if it is free on every segment.
  • The database prevents double booking: seat_reservation has the primary key (trip_id, seat_id, segment_index); Oracle error ORA-00001 means "seat taken".
  • The hold lasts 5 minutes from the first pick; later picks join and never extend it. A sweeper runs every second and releases expired holds.
  • Payment wins: if Stripe says the money was taken, the booking is confirmed even if the hold has just run out. A timeout never charges and never refunds.
  • Calls that must not be lost go through an outbox table with a retry job (ticket, email, refund requests, payment results).
  • Admins can also confirm a booking without Stripe (paid at the counter, or complimentary); see docs/design/COUNTER-BOOKING.md.

Who calls whom

  • The browser talks to the Gateway only (and to Keycloak directly for login). The Gateway has no Keycloak proxy; it only fetches Keycloak's public keys (JWKS) and caches them.
  • Gateway to Train & Schedule and to Booking & Seat. The Gateway forwards the user's JWT; each Spring service validates it again as an OAuth2 resource server.
  • Train & Schedule to Booking & Seat: pushes the trip snapshot (PUT /internal/trips/{id}/snapshot) when a trip is created or edited.
  • Booking & Seat to Payment, Ticket, Notification and Train & Schedule (mark a trip cancelled). Payment to Booking & Seat (payment result, refund status).
  • Payment to Stripe. Notification to SMTP.
  • Service-to-service calls carry a shared secret in the header X-Internal-Api-Key (paths /internal/**). The Gateway never forwards that header and never routes /internal/**. The only entry without a login is the Stripe webhook, which is authenticated by Stripe's signature.
  • A service never reads another service's tables. The user is identified by the JWT sub as a plain value, never as a foreign key.

Data ownership

Each service has its own Oracle schema and its own Flyway migrations (src/main/resources/db/migration). Booking & Seat keeps its own copy of seats and standing capacity (tables trip, trip_stop, trip_coach, trip_seat, trip_fare), so availability never needs a join into Train & Schedule. A copy must be kept current: that is the snapshot push, and the re-publish when trains, coaches, seats, fares, routes or stations change (TripSnapshotRefresher in Train & Schedule).

The patterns used everywhere

  • Layers inside a Spring service: controller (HTTP only), service (rules), repository (SQL with JdbcClient, no JPA). Packages are feature first, then layer.
  • Database-enforced rules. seat_reservation has the primary key (trip_id, seat_id, segment_index); a second insert fails with ORA-00001, which the code reads as "seat taken". Standing places use conditional UPDATEs (check the updated row count) and a CHECK used <= capacity.
  • One lock order: trip row, then booking row, then seat or standing rows, then the version counter (BookingLocks). It avoids deadlocks.
  • Full-journey availability: a journey from stop i to stop j uses segments i..j-1; a seat is available only if it is free on every one (availability/service/SegmentAvailability).
  • No call to another service or to Stripe inside an open DB transaction. The code decides in a short transaction, calls outside, then records in a second short transaction that re-checks.
  • Outbox plus retry poller instead of a message broker. A row in an outbox table is written in the same transaction as the state change; a @Scheduled job delivers it with a backoff. Used by Booking (ticket and email, ticket invalidation, refund request, cancellation email), Payment (payment result and refund status to Booking) and Notification (its email table is the outbox).
  • Idempotency: calls that may be repeated are safe to repeat (PUT of a ticket, MERGE of a snapshot, the Stripe idempotency key, the webhook event id as a primary key, the dedupeKey of emails).
  • Events after commit: live updates are published inside the transaction but delivered only by @TransactionalEventListener(AFTER_COMMIT).
  • Audit: every admin action and booking state change writes an audit_log row (same transaction) and a log line from the logger audit (after commit), shipped to OpenObserve.
  • Server-side money: amounts are always computed from the held seats and the stored fares, never taken from the client.

Booking states

PENDING_PAYMENT (the hold) leads to CONFIRMED (paid by card, or issued by an admin), or to EXPIRED (timeout, or the trip was cancelled), or to ABANDONED (the user released the last item). CONFIRMED leads to CANCELLED. The refund state is a separate column refund_status (NONE, REFUND_PENDING, REFUNDED, REFUND_FAILED, and for counter bookings NOT_APPLICABLE, MANUAL_REFUND_DUE, REFUNDED_AT_COUNTER). The booking's payment_method is CARD, COUNTER or COMPLIMENTARY (see docs/design/COUNTER-BOOKING.md). Booking's copy of a trip is OPEN, CANCELLING or CANCELLED; Train & Schedule's trip is ACTIVE or CANCELLED.

Security in short

Keycloak issues the JWT (authorization code with PKCE). The Gateway (gateway/src/auth.js: authenticate, requireAuth, requireRole) verifies signature, expiry and role; admin paths answer 403 to non-admins. Each Spring service checks the JWT again. Internal paths need the shared key. Stripe's webhook needs a valid signature. Card data goes from the browser to Stripe (Payment Element) and never touches our servers.

2. End-to-end walkthroughs

Nine journeys through the code. Each lists the steps in order, with the file and method that does each step. Paths are relative to the repository root. Abbreviations: B = services/booking-seat/src/main/java/com/trainbooking/bookingseat, P = services/payment/src/main/java/com/trainbooking/payment, T = services/ticket/src/main/java/com/trainbooking/ticket, N = services/notification/src/main/java/com/trainbooking/notification, TS = services/train-schedule/src/main/java/com/trainbooking/trainschedule, FE = frontend/src, GW = gateway/src.

1. Search

  1. FE/pages/SearchTrips.tsx (with FE/components/SearchForm.tsx) loads stations with GET /stations and sends GET /trips?from=<code>&to=<code>&date=.
  2. GW/app.js routes GET /trips through requireAuth (GW/auth.js) to tripSearch() in GW/search.js.
  3. tripSearch forwards the call to Train & Schedule: TS/trip/controller/TripSearchController.search then TS/trip/service/TripSearchService, which reads TS/trip/repository/TripRepository (active trips, origin before destination, departure date at the origin, journey fare per class = sum of the segment fares, all stops with times in one query).
  4. Back in the Gateway, fetchAvailabilitySummary (same file) asks Booking & Seat for each trip in parallel: GET /trips/{id}/availability?from=&to=&view=summary (B/availability/controller/AvailabilityController.availability, AvailabilityService.availability, the pure rule SegmentAvailability.compute). It adds availability: { seatsLeft, standingLeft } per class, or null if Booking does not answer within AVAILABILITY_TIMEOUT_MS (the timetable still shows).
  5. The page shows the trips; "Select seats" opens /trips/:id/seats.

The seat map (FE/pages/SeatMapPage.tsx) calls GET /trips/{id}/seat-map?from=&to=. GW/seatmap.js (seatMap, composeSeatMap) fetches the layout from Train & Schedule (TripLayoutController.layout / TripLayoutService) and the availability from Booking in parallel, and merges them. A seat unknown to Booking is shown as booked.

2. Seat hold and live updates

  1. The user clicks a seat in FE/pages/SeatMapPage.tsx (drawn by FE/components/CoachSeats.tsx, SeatShape.tsx). The page sends POST /bookings/pick {tripId, fromStop, toStop, seatId} or {..., coachId, qty} for standing places.
  2. GW/app.js: app.use('/bookings', requireAuth, ...) forwards to Booking. B/booking/controller/BookingController.pick builds the caller from the JWT (sub, email, name) and calls B/booking/service/HoldService.pick.
  3. HoldService.pick: checked (the token must have an e-mail), prepare (validates the trip is OPEN and not departed, the stops and the seat or coach; prices the journey with BookingPricing), then pickInTransaction in ONE transaction. The lock order is fixed by BookingLocks: the trip row first (inventory.lockTrip), then the user's active booking row. The first pick creates the booking (insertBooking: PENDING_PAYMENT, expires_at = now + 5 min; the unique index uk_booking_active_hold allows one active hold per user and trip). Later picks join it and never change expires_at. pickSeat inserts one seat_reservation row per segment in sorted order; an ORA-00001 means the seat is taken (409 seats_unavailable for that pick alone). pickStanding does a conditional UPDATE standing_usage per segment and checks the updated row count.
  4. Still inside the transaction, AvailabilityEvents.seats / standing (B/live/AvailabilityEvents.java) take the next per-trip version number and publish a SeatEvent (HELD); AvailabilityEvents.toUser sends the holder a UserEvent. Pricing is recomputed from the booking's items after each pick.
  5. Only after the commit, B/live/LiveUpdates.seatEvent and userEvent (@TransactionalEventListener(AFTER_COMMIT)) send the messages through SimpMessagingTemplate to /topic/trips/{tripId} and /user/queue/holds.
  6. The browser listens through FE/live/connectLive.ts (STOMP over WebSocket, token in the subprotocol). The connection goes to the Gateway GW/wsproxy.js (attachWebSocketProxy: verifies the token on the HTTP upgrade, checks the origin, pipes to Booking). In Booking, B/live/WebSocketConfig, HandshakeAuthentication (reads the JWT from the subprotocol) and SubscriptionGuard (only SUBSCRIBE to the trip topic and the user queue) accept it.
  7. FE/live/applySeatEvent.ts applies the event to the seat map: it drops stale versions and reloads the full availability on a version gap or after a reconnect.
  8. Release: POST /bookings/{id}/release (BookingController.release then HoldService.release, which ends the hold as ABANDONED when the last item goes, through HoldReleaseService.release) or DELETE /bookings/{id}/hold (releaseAll). Before any change, HoldService.settlePaymentBefore asks Payment to invalidate or cancel a payment already started.

3. Card payment and the Stripe webhook

  1. "Continue to payment" in SeatMapPage calls POST /bookings/{id}/payment: BookingController.startPayment then B/booking/service/PaymentStartService.start. Under the booking lock it re-checks the hold and sets payment_started (never cleared); then, outside any transaction, it calls Payment through B/payment/PaymentClient (PaymentPort).
  2. Payment: P/payment/controller/PaymentController (POST /internal/payments) then P/payment/service/PaymentService.create. It locks the payment row of the booking, decides in a short transaction, calls Stripe outside any transaction through P/stripe/StripeGateway (real implementation StripeApiGateway; test keys only, guarded by StripeKeyGuard), then records the PaymentIntent in a second transaction. The Stripe idempotency key is payment-<booking>-r<revision>. The answer carries the client secret.
  3. FE/pages/PaymentPage.tsx shows the countdown (FE/countdown.ts) and FE/components/StripeCheckout.tsx, which loads Stripe.js and calls confirmPayment (Payment Element). Card data goes to Stripe only.
  4. Stripe sends payment_intent.succeeded to POST /webhooks/payment. GW/app.js takes the raw body (express.raw, the signature covers exact bytes) and forwards only Content-Type and Stripe-Signature to P/webhook/controller/WebhookController, then P/webhook/service/WebhookService.handle: verify the signature (Webhook.constructEvent, 5 min tolerance), then ONE transaction process: insert the event id into webhook_event (a duplicate gives ORA-00001, answered as DUPLICATE) and apply the effect: paymentEvent locks the payment row (findByIntentForUpdate) and calls PaymentService.recordSuccess, which queues a PAYMENT_RESULT row in Payment's outbox.
  5. P/outbox/service/OutboxScheduler runs OutboxDispatcher.dispatchDue, which calls HttpBookingNotifier to send POST /internal/bookings/{id}/payment-result to Booking (retries 2..60 s, in order per booking).
  6. Booking: B/booking/controller/InternalPaymentController.paymentResult then PaymentResultService.paymentSucceeded. The paid amount must equal the booking's amount, even if the five minutes have just run out (payment wins). Then ConfirmationService.confirm / confirmLocked (one transaction under the locks): the reservations lose their expiry, the booking becomes CONFIRMED, a SEAT_BOOKED event is published (delivered after commit), and a TICKET_EMAIL job is queued in the same transaction. A different amount or a gone hold ends the hold and answers REFUND_REQUIRED; Payment then refunds (RefundService.request).
  7. The payment page waits for the server's CONFIRMED (it never trusts the browser result) and moves to /bookings/:id/ticket.

4. Ticket and email

  1. ConfirmationService queued TICKET_EMAIL in B/outbox (written by OutboxWriter.queue, which requires the confirming transaction).
  2. B/outbox/service/OutboxScheduler (every second) calls OutboxDispatcher.dispatchDue, which runs the due jobs, jobs of one booking in order. TicketEmailJob.run does the work.
  3. TicketEmailJob.run calls Ticket (B/ticket/TicketClient): PUT /internal/tickets/{bookingId} handled by T/ticket/controller/TicketController and T/ticket/service/TicketService.issue (201 for a new ticket, 200 for an existing one; a repeat never revives an invalidated ticket). QrTokens signs the QR payload (reference.nonce.HMAC-SHA256), QrImages draws the QR with ZXing, TicketPdfRenderer builds the one-page PDF with OpenPDF; the PDF is stored as a BLOB in table ticket.
  4. The job reads the PDF (GET /internal/tickets/{id}/pdf) and calls Notification (B/notification/NotificationClient): POST /internal/notifications handled by N/notification/controller/NotificationController and NotificationService.accept, which stores the email (text and HTML from EmailTemplates, the PDF as attachment, a dedupeKey) and answers 202.
  5. N/notification/service/EmailScheduler runs EmailDispatcher.dispatchDue every second; N/mail/SmtpEmailSender sends by Spring Mail (Mailpit in dev, port 1025). A failure backs off 2..300 s and is FAILED after 300 attempts. An email or ticket failure never changes the booking.
  6. The user can open the ticket in the browser: GET /bookings/{id}/ticket and /ticket/qr (GW/ticket.js: ticketPdf, ticketQr, after an owner check in Booking). "Resend ticket" in FE/pages/MyBookingsPage.tsx calls POST /bookings/{id}/resend-ticket (TicketResendService.resend, queues TICKET_EMAIL unless one is waiting).

5. Cancellation and refund

  1. The passenger clicks Cancel in FE/pages/MyBookingsPage.tsx (with a confirmation step): POST /bookings/{id}/cancel, BookingController.cancel, owner check by sub (another user's booking gives 404). An admin does it as support from FE/components/BookingAdminPanel.tsx (page SupportPage): POST /admin/bookings/{id}/cancel with a reason, AdminBookingController.cancel (Gateway: ADMIN only).
  2. Both call B/booking/service/CancellationService.cancel(Actor, id, reason); Actor.user / Actor.admin carries the id and role. cancelInTransaction runs ONE transaction under BookingLocks: re-checks CONFIRMED and the cutoff (the booking's own boarding stop has not departed; else 409 trip_departed; not confirmed: 409 not_cancellable), gives the seats back (BookingInventory.giveBack, which publishes RELEASED events), sets CANCELLED with cancelled_by, cancelled_by_role, cancelled_at (and cancel_reason for an admin) and refund_status by payment method (CARD: REFUND_PENDING; COUNTER: MANUAL_REFUND_DUE; COMPLIMENTARY: NOT_APPLICABLE), and queues TICKET_INVALIDATE, CANCELLATION_EMAIL and, for CARD only, REFUND_REQUEST in the outbox. An already cancelled booking is returned as it is. Stripe is only ever asked for a card booking (full refund).
  3. The outbox jobs (B/outbox/service/CancellationJobs, run by OutboxDispatcher): invalidate the ticket (T/.../TicketService.invalidate), ask Payment for the refund (B/payment/RefundPort to POST /internal/refunds, P/refund/service/RefundService.request then attempt, which calls Stripe outside a transaction), send the cancellation email.
  4. Stripe confirms with the refund.updated webhook (same path as walkthrough 3): WebhookService.process then RefundService.applyStripeEvent, which queues a REFUND_STATUS message. Payment's outbox delivers it to POST /internal/bookings/{id}/refund-status (InternalPaymentController.refundStatus, PaymentResultService.refundStatus), which sets REFUNDED and queues the REFUND_EMAIL once (REFUND_FAILED is only flagged for follow-up). RefundRetrier retries refunds that could not be sent.

6. Counter and complimentary booking

Rule: docs/design/COUNTER-BOOKING.md. An admin confirms a hold without Stripe.

  1. The admin opens the board (FE/pages/TripsBoard.tsx, shown in SupportPage), opens a trip (FE/components/BoardDetailPanel.tsx) and picks seats with FE/components/AdminSeatPicker.tsx, which uses the normal POST /bookings/pick with the admin's own token (the hold belongs to the admin) and the same live updates.
  2. FE/components/IssueBookingForm.tsx collects the method (COUNTER or COMPLIMENTARY), the note or the reason (5 to 500 characters for complimentary), and the passenger: an existing account (looked up by exact email with GET /admin/passengers/lookup, AdminBookingController.lookup, BookingIssueService.lookup) or a walk-in (name, optional phone and email).
  3.   4. The ticket and email follow as in walkthrough 4. A walk-in without an email gets a ticket but no email.
  5.   1. The admin uses FE/components/TripCancellation.tsx on the admin Trips page (FE/pages/Trips.tsx): POST /admin/trips/{id}/cancel { reason }, then GET /admin/trips/{id}/cancellation to show progress.   2. Then process runs.
  3. process(tripId) is safe to call many times: (a) tell Train & Schedule (B/schedule/TrainScheduleClient.markTripCancelled to TS/trip/controller/InternalTripController.cancel, idempotent, no push back); (b) for each active hold releaseHold cancels its payment first and releases it as EXPIRED with the reason TRIP_CANCELLED ("This trip was cancelled"); (c) for each confirmed booking CancellationService.cancelForTrip as the admin, without the boarding-stop cutoff, so refunds, ticket invalidation and emails follow as in walkthrough 5; (d) when nothing is PENDING_PAYMENT or CONFIRMED any more and Train & Schedule was told, markCancelled sets CANCELLED and AvailabilityEvents.tripCancelled pushes TRIP_CANCELLED after commit.
  4. TripCancellationWorker (every 5 s) calls process again for trips still CANCELLING, so a failed step is retried. In the UI CANCELLING reads "CANCELLED - bookings pending".

9. Hold expiry and the sweeper

  1. B/booking/service/HoldSweeper.sweep (@Scheduled(fixedDelayString = "${trainbooking.sweeper.fixed-delay-ms:1000}")) calls ExpiryService.sweep outside any transaction.
  2. ExpiryService.sweep reads the due holds (BookingRepository.findDueHoldIds: PENDING_PAYMENT, expires_at past, next_attempt_at due) and calls expire(id) for each, catching errors one by one so one bad booking never stops the others (failure leads to retryLater, a backoff 2, 4 ... 60 s in next_attempt_at).
  3. ExpiryService.expire refuses to run inside a transaction. If the booking never opened the payment page (payment_started false) there is nothing to cancel. Otherwise it asks Payment first: PaymentPort.cancelPending (PaymentClient to P/payment/service/PaymentService.cancelPending, which cancels the Stripe PaymentIntent or reports it already SUCCEEDED or PROCESSING).
    • NONE or CANCELLED: HoldReleaseService.release(..., EXPIRED, onlyIfPastExpiry = true, "system", ...) in one transaction under the locks gives the seats back (BookingInventory.giveBack), sets EXPIRED and publishes RELEASED plus a HOLD_EXPIRED user event after commit. If the payment page was opened in the meantime, PaymentStartedMeanwhileException rolls back and the next sweep asks Payment.
    • SUCCEEDED or PROCESSING: nothing is released; the sweeper asks again in 1 s. A succeeded payment confirms the booking only through Payment's own report (walkthrough 3, step 6). Booking never confirms by itself in the sweeper.
    • Payment unreachable (PaymentUnavailableException): retryLater with backoff; the seats stay held.
  4. The browser: FE/pages/PaymentPage.tsx and SeatMapPage.tsx react at once to the HOLD_EXPIRED user event (or to the booking being EXPIRED when polled) and redirect to the seat map with the message "Your 5 minutes ran out. The seats were released, please select again." An expired hold that is not yet released still shows as held to everyone else (the availability query never reads the clock).

3. Train & Schedule service

Purpose

Train & Schedule owns the timetable data: stations, trains, coaches (with standing capacity), seats, routes with ordered stops, fares per route segment per coach class, and trips. Admins edit all of it. Passengers only search trips and read the station list.

It does not sell anything. Booking & Seat keeps its own copy of every trip (a "snapshot"), and Train & Schedule pushes that copy whenever a trip, or something inside a trip, changes. A service never reads another service's tables, which is why the copy exists.

  • Port 8081. Oracle schema (database user) train_schedule. Spring Boot, Spring MVC, Spring JDBC (JdbcClient, no JPA, so the SQL is explicit), Flyway.
  • Called by the Gateway with the user's Keycloak JWT, and by Booking & Seat with the shared internal API key.
  • Calls Booking & Seat (PUT/DELETE /internal/trips/{id}...) on every trip change.

Important code paths, step by step

A. Admin creates a trip (the main path)

  1. Gateway checks token and ADMIN, forwards POST /admin/trips. SecurityConfig checks again. TripController.create validates the body (@Valid).
  2. TripService.create (one transaction) calls plan(...): train and route exist (400 otherwise), train is ACTIVE, train has coaches, stop count equals route stop count, TripTimeline.resolve turns HH:mm into date-times (a time earlier than the previous one means next day; max 24 h), and requireCompleteFares checks there is a fare for every segment and every class the train has.
  3. TripRepository.insert + insertStops (JDBC batch), then AuditTrail.change (row now, log line after commit).
  4. Last step: TripSnapshotPublisher.publish builds the snapshot and BookingSeatClient.putSnapshot sends it. If Booking says 409/400/5xx or is down, an exception is thrown and Spring rolls back everything above. A trip therefore exists here only if Booking accepted it.

B. Editing something inside trips (train, coach, seat, fare, route, station)

  1. The edit service saves its change and writes its audit row, then calls SnapshotChanges.trainChanged / routeChanged / stationChanged.
  2. TripSnapshotRefresher.register stores the change on the current transaction and registers a beforeCommit callback once. Several edits in one request give one push per trip.
  3. Just before the commit the callback finds the future, ACTIVE trips (first stop departs after now) of that train/route/station and publishes each once. If Booking refuses (for example a reserved seat would be removed: capacity_conflict), the commit fails and the edit is rolled back. Trips that already left keep their old copy.

C. Trip search

TripSearchService.search: both station codes must exist and differ; the window is the local day (for today it starts at "now"); one SQL query finds trips whose origin stop comes before the destination stop; the stops of all matches are loaded with one query; fares are the sum of segments fromStop..toStop-1 per class. No match: the next date with a trip is returned. The Gateway then adds seats left from Booking & Seat.

D. Whole-trip cancel (Flow 8, step 3)

Booking calls POST /internal/trips/{id}/cancel with the API key; TripService.markCancelled sets CANCELLED (idempotent) and audits. No snapshot is pushed back.

Known limits

See also chapter 13. For this service:

  • Duplicate and "in use" errors are recognised by searching the database error text for a constraint name (UK_COACH_POSITION, FK_ROUTE_STOP_STATION ...). Renaming a constraint in a migration would silently turn these 409 answers into 500.
  • TripRepository.findStops uses an IN (:ids) list; Oracle allows at most 1000 values (ORA-01795). A search or admin list returning more than 1000 trips would fail.
  • GET /admin/trips and the admin lists have no paging.
  • TripLayoutService runs one seat query per coach.
  • The push to Booking happens inside the database transaction, so an admin request holds a connection while Booking answers (up to 5 s read timeout). The rare gap (Booking accepts, then the local commit fails) is documented in TripSnapshotPublisher.
  • A trip's status can be CANCELLED and TripService.update does not check it; Booking refuses the push (trip_not_open), which protects the data.
  • JsonErrorHandlers.handle always says "The ADMIN role is required", also for the internal chain.
  • audit_log.admin_id is 64 characters; the X-Acting-User header is stored as given, so a longer value would make the cancel fail with a 500.

4. Booking & Seat service

Purpose

Booking & Seat is the heart of the system. It decides who may sit where, and it is the only service that changes the state of a booking. It owns:

  • the copy of every trip (stops, coaches, seats, standing capacity, fares) that Train & Schedule pushes to it (the "snapshot");
  • segment availability: which seats and standing places are free for a journey;
  • the 5-minute hold (seats picked but not yet paid), the sweeper that releases expired holds, and the live seat updates;
  • bookings: confirmation after payment, cancellation by the passenger, by an admin, and for a whole trip;
  • counter and complimentary bookings made by an admin without Stripe;
  • the outbox that calls Ticket, Notification and Payment (refund) later, with retries;
  • the read side for "My bookings", admin support search, and the live trips board.
  • Port 8082. Oracle schema (database user) booking_seat. Spring Boot, Spring MVC, Spring JDBC (JdbcClient, no JPA), Spring WebSocket (STOMP), Flyway.
  • Called by the Gateway with the user's Keycloak JWT; by Train & Schedule (snapshot) and Payment (payment result, refund status) with the shared internal API key.
  • Calls Payment (create, invalidate and cancel a payment, request a refund), Ticket, Notification and Train & Schedule (mark a trip cancelled), all over REST with the internal API key.

Important code paths, step by step

A. Picking a seat (Flow 3), HoldService.pick

  1. BookingController.pick validates the body and takes the caller from the JWT (AuthenticatedUser.of). The token must carry an e-mail.
  2. prepare (no lock): exactly one of seat or coach; the trip exists and is OPEN; the journey fits the trip; the seat or coach is on this trip; the price comes from the fares of the trip copy (BookingPricing).
  3. If the user's active hold already had payment_started, settlePaymentBefore asks Payment first to invalidate the open payment (outside any transaction). SUCCEEDED becomes 409 already_paid, PROCESSING 409 payment_in_progress.
  4. pickInTransaction (one transaction): lock the trip row (FOR UPDATE); refuse if the trip is not OPEN or the boarding stop has left; lock the user's active hold row.
    • No hold yet: insert the booking with expires_at = now + 5 minutes. Hold exists: it must not be over (410), must be for the same journey (409), and expires_at is never changed.
    • Seat: INSERT one seat_reservation row per segment (sorted). If any row exists, Oracle raises ORA-00001 and the whole pick rolls back. Standing: UPDATE standing_usage SET used = used + qty WHERE ... AND used + qty <= capacity per segment in ascending order; a row count of 0 means "gone".
    • Recompute the booking amount from its lines, publish SEAT_HELD / STANDING_CHANGED (takes the next trip_version, delivered after the commit), write the audit row.
  5. A DuplicateKeyException, StandingUnavailableException or lock timeout becomes 409 seats_unavailable for that pick only; earlier picks stay held.

B. The sweeper and the 5-minute rule (Flow 5), HoldSweeper -> ExpiryService

  1. Every second findDueHoldIds returns PENDING_PAYMENT bookings with expires_at <= now whose next_attempt_at is empty or due.
  2. For each, outside any transaction: if payment_started, ask Payment to cancelPending first. NONE/CANCELLED: call HoldReleaseService.release (lock trip and booking, re-check, give seats back, set EXPIRED, send HOLD_EXPIRED to the user after commit). SUCCEEDED/PROCESSING: keep the seats, retry in 1 s; Payment's own report will confirm the booking (the sweeper never confirms by itself). Payment down: backoff 2, 4, ... 60 s in next_attempt_at.
  3. A hold whose owner never opened the payment page is released without calling Payment, so a Payment outage cannot block seats. The release re-checks payment_started under the lock; if the page was opened meanwhile it throws PaymentStartedMeanwhileException and the next sweep asks Payment.
  4. Until released, an expired hold keeps blocking its seat and the availability query shows it as held, never free (that query never reads the clock).

C. Payment wins, PaymentResultService.paymentSucceeded -> ConfirmationService

  1. Payment reports { amount }. If the booking is still a hold and the amount differs from the booking's, the hold is ended and the answer is REFUND_REQUIRED (Payment refunds).
  2. Otherwise ConfirmationService.confirm: lock trip and booking; if PENDING_PAYMENT set expires_at to NULL on its reservations, set CONFIRMED, publish SEAT_BOOKED, queue TICKET_EMAIL in the outbox, audit. This works even if the five minutes have just run out, as long as the hold was not released yet.
  3. A booking that is already EXPIRED, ABANDONED or CANCELLED returns NOT_CONFIRMABLE, so the report answers REFUND_REQUIRED. A repeated report is harmless (ALREADY_CONFIRMED answers CONFIRMED).
  4. The counter and complimentary path (BookingIssueService) uses the same confirmLocked, with no Stripe: it records payment_method, who issued it and what was charged.

D. Cancellation (Flow 6), CancellationService

  1. One transaction under BookingLocks: owner check (404 for another user), already CANCELLED returns as is, a passenger cannot cancel a desk-issued booking, only CONFIRMED can be cancelled, the cutoff (departure of the booking's own boarding stop still ahead) gives 409 trip_departed.
  2. BookingInventory.giveBack, then markCancelled with cancelled_by, cancelled_by_role and (admin only) cancel_reason; refund_status is REFUND_PENDING (card), MANUAL_REFUND_DUE (counter) or NOT_APPLICABLE (complimentary).
  3. Queue in the outbox, in this order: TICKET_INVALIDATE, REFUND_REQUEST (card only), CANCELLATION_EMAIL; audit.
  4. Later, OutboxDispatcher runs them: invalidate the ticket, ask Payment for the full refund (never gives up; flagged REFUND_FAILED after 8 failed attempts so support sees it), e-mail the passenger. Payment's REFUNDED report queues REFUND_EMAIL once.

E. The outbox, OutboxWriter -> OutboxDispatcher

A job row is written in the same transaction as the change, so they stand or fall together. The dispatcher runs jobs outside transactions; success marks SENT, failure reschedules with 2^attempt seconds (max 300), after 300 attempts FAILED (not for refunds). Order is kept per booking only where it matters (ticket issue before invalidate).

F. Whole-trip cancel (Flow 8), TripCancellationService

request locks the trip and sets CANCELLING (closed to new picks at once). Each process pass: tell Train & Schedule, cancel each hold's payment then release it, cancel each confirmed booking without the cutoff, and when nothing is left mark the trip CANCELLED and push TRIP_CANCELLED. The worker repeats it every 5 s.

G. The snapshot, SnapshotService.apply

Lock the trip row; refuse a non-OPEN trip; if reservations or paid bookings exist, refuse changes to date, train, stops, times and fares and (with reservations) capacity losses; then MERGE trip, stops, coaches, seats, standing counters and fares in foreign-key order; audit. Any failure rolls back, and Train & Schedule rolls its own change back.

H. Live updates

AvailabilityEvents publishes inside the transaction; LiveUpdates (@TransactionalEventListener(AFTER_COMMIT)) sends to /topic/trips/{id} or /user/queue/holds. The handshake checks the JWT from the subprotocol; SubscriptionGuard allows only two kinds of SUBSCRIBE and refuses SEND.

Known limits

See also chapter 13. For this service:

  • AdminBookingQueryService.toAdminView and BookingQueryService.toView read the trip info and items with separate queries per booking (and two queries per stop): up to 100 bookings in a search and 50 in "My bookings" cost hundreds of small queries.
  • The support search uses UPPER(reference) = :ref, which cannot use the unique index on reference.
  • BookingRepository.findPassengersByEmail knows only users who already have a booking, and excludes the literal user id demo-passenger.
  • The STOMP broker is in memory: with two instances of this service, a client would only get the events of the instance it is connected to.
  • OutboxDispatcher runs jobs one after another in one thread (20 per tick). A slow Ticket or Notification (10 s read timeout) delays every other job.
  • A late-paid hold on a CANCELLING trip is confirmed and then refunded (by the next pass) instead of being refused when the user clicks "Continue to payment".
  • HoldService.pick maps a lock timeout (PessimisticLockingFailureException) to "seats unavailable", which can be a slightly misleading message for a busy database.
  • ExpiryService.retryLater only logs an error from the 5th attempt; a hold whose release keeps failing stays held until someone looks at the log.
  • JsonErrorHandlers.handle always says "The ADMIN role is required.", also if the 403 comes from another rule.
  • V1__create_snapshot_and_reservation_tables.sql still contains a TODO(slice 7) comment that is done (migrations are never edited, because Flyway checks their checksum).
  • Test smell: FakeTicketPort.issue has a redundant !issueCalls.isEmpty() test (it is always true after the add).

5. Payment service

Purpose

Payment owns everything that touches Stripe: creating the payment of a booking, cancelling it when the hold ends or changes, checking Stripe's webhook, and refunding. Users never call it. Booking & Seat calls it (with the shared API key) and Stripe calls it (through the Gateway).

Why a separate service: the Stripe secret key and the webhook secret live only here, and card data never reaches our servers at all. The browser sends the card straight to Stripe; Payment only hands the page a client secret (the key to one payment intent) and the publishable key.

  • Port 8083. Oracle schema (user) payment. Spring Boot, Spring MVC, Spring JDBC (JdbcClient), Flyway, Stripe Java 34.1.0.
  • Test mode only. StripeKeyGuard stops the service at start-up if a key does not start with sk_test_, pk_test_ or whsec_.
  • Cards only, EGP, amounts in piastres (amount x 100, exact). Stripe's minimum charge is about US$0.50 (roughly EGP 27): below it, 409 amount_too_small.

Key code paths, step by step

Rule for all of them: every change locks the payment row first (SELECT ... FOR UPDATE, PaymentRepository.findByBookingForUpdate), and Stripe is never called inside a transaction. The pattern is: short transaction that decides, then the Stripe call, then a short transaction that records the result and re-checks that nothing changed.

  1. Create (PaymentService.create). Refuse when no Stripe key or no publishable key (nothing written). Transaction 1 (claimForCreation): no row, insert CREATING (a clash on the unique key is ORA-00001, shown as payment_in_progress); a closed row is payment_closed; SUCCEEDED is already_paid; PROCESSING is payment_in_progress; PENDING with the same amount is reused, with another amount payment_outdated; an old CREATING (over 60 s) is taken over; CANCELLED restarts as the next revision. Then StripeGateway.createIntent with key payment-<booking>-r<revision>. Transaction 2 (attachIntent): if the row was cancelled meanwhile the intent is cancelled and the caller gets 409 (the secret is never handed out, so nobody can pay for seats that are being released).
  2. Cancel and invalidate (cancel, planCancel, settleCancel). cancel = the hold ended: the row gets ended = 1, or a tombstone (closed row, no intent) when there was no row, so a creation already on its way is refused. invalidate = the booking changed: the intent is cancelled and a new revision may follow. If Stripe says succeeded, the payment wins: recordSuccess queues the news and the answer is SUCCEEDED. If processing, the answer is PROCESSING and Booking keeps the seats and asks again. If Stripe is down: 503, the row stays as it was.
  3. Webhook (WebhookService.handle). Secret set? Header present? Webhook.constructEvent verifies the signature and the 5 minute tolerance. Then one transaction: insert webhook_event (duplicate: DUPLICATE), apply the event (recordSuccess writes an outbox row in the same transaction). A failure rolls back the insert too, so Stripe's retry works.
  4. Outbox (OutboxDispatcher.dispatchDue, every second). Takes up to 20 due messages, one per booking at a time (older pending message first, NOT EXISTS in findDue), calls Booking (no transaction), marks SENT. Transient failure: backoff 2, 4 ... 60 s. Booking refuses for good (404/400): PAYMENT_RESULT triggers a refund, then the message is FAILED. If Booking answers REFUND_REQUIRED (hold gone or amount differs), a refund is requested too. So money taken always ends as a booking or a refund.
  5. Refund (RefundService.request, attempt). Needs a SUCCEEDED payment. Transaction: insert the refund (PENDING), outbox REFUND_PENDING, audit. Then Stripe with key refund-<id>. Stripe unreachable: stays PENDING, RefundRetrier retries (backoff to 60 s, logged every hour, never given up). Stripe refuses for good (4xx): FAILED at once. The result or a refund.updated webhook sets SUCCEEDED or FAILED once; a final refund never changes again. A timeout never reaches this code (FR-P4).

6. Ticket service

Purpose

Important code paths, step by step

A. Issue a ticket (TicketService.issue)

  1. Booking & Seat confirms a booking and its TICKET_EMAIL job calls PUT /internal/tickets/{bookingId}.
  2. Spring Security runs InternalApiKeyFilter: wrong key means 401 and no controller runs. Then @Valid checks the body (400 on failure).
  3. TicketService.issue (one transaction) first looks for a ticket of this booking. If there is one, it returns it unchanged with created = false (200). This is also true for an invalidated ticket, so a repeat never revives a cancelled ticket.
  4. Otherwise QrTokens.issue makes reference.nonce.signature (12 random bytes, HMAC-SHA256 with TICKET_SIGNING_KEY).
  5. TicketPdfRenderer.render draws the PDF with that token inside the QR; QrImages.png draws the QR at 900 px so the print stays sharp.
  6. TicketRepository.insert stores the row. The UNIQUE (booking_id) key makes a second ticket impossible: if two calls race, the loser gets DuplicateKeyException (ORA-00001) and answers with the winner's ticket.
  7. An audit_log row (CREATE) is written in the same transaction; the audit log line goes out after the commit. The answer is 201.

B. Invalidate (TicketService.invalidate)

  1. A cancelled booking queues TICKET_INVALIDATE; the job calls POST .../invalidate.
  2. The row is read with SELECT ... FOR UPDATE, so two invalidations run one after the other.
  3. If VALID: UPDATE ... WHERE status = 'VALID' sets INVALIDATED and the time, and an INVALIDATE audit row is written. If already invalidated: returned as it is.
  4. The PDF stays as the record. Missing ticket: 404 (Booking & Seat retries until the issue job has made it).

C. The QR code

The token has three parts separated by dots: the reference, a random nonce and the signature. Nobody without the key can make or change one (QrTokens.verify checks it in constant time). The token says nothing about validity: whether the ticket is still good is the status of its row. No service calls verify today; it is ready for a gate scanner. The page copy of the QR comes from GET .../qr, drawn from the stored token with the same method as the PDF.

D. The PDF

TicketPdfRenderer draws one A5 landscape page by absolute coordinates: card, header with logo, route with big times (converted to TIMEZONE), a grid of facts (date, train, passenger, class, coach, seats or places), the QR panel with the reference, and a footer with the payment line. Built-in fonts only, and every text goes through safe() so an unusual name never breaks the rendering. A long seat list shrinks and ends with "and N more" only as a last resort.

Tests

Unit tests need no database: QR tokens, QR images and the PDF (text read back from the file). The database tests use the schema ticket_test and are skipped, not passed without TICKET_TEST_DB_PASSWORD. Counting the @Test methods: 6 + 3 + 15 + 8 + 7 = 39 (24 without a database, 15 with).

Known limits

  • QrTokens.verify has no caller yet: there is no gate-scanner endpoint (not in the SRS list of endpoints).
  • The QR token is a bearer secret; the answer of /qr and the PDF contain it, so only trusted services may call these routes (they are internal-only).
  • The PDF is drawn before the INSERT, inside the transaction; a race loser draws a PDF that is thrown away.
  • RequestValidationException and AuditTrail.change are shared code that this service does not use.
  • The audit actor is always booking-service (the real user is not known here), and the column is named admin_id.
  • Only English text; characters outside the Windows-1252 set (Arabic, emoji) are replaced by ? on the PDF.
  • The logo needs a PNG file (OpenPDF cannot draw SVG); without it the PDF has a plain header.

7. Notification service

Purpose

Notification owns the emails of the system: the ticket email, the cancellation email and the refund email. Nobody outside the backend calls it. Booking & Seat asks it for an email from its outbox (see chapter 4). The request is stored and answered at once (HTTP 202). A background poller sends the email by SMTP afterwards, with retries. So a mail server that is down, or an address that is refused, can never fail the payment, the confirmation or the cancellation that asked for the email (rule: an email failure never cancels a booking).

  • Called by Booking & Seat only, with the shared key in X-Internal-Api-Key. The Gateway never routes to it.
  • Calls an SMTP server: Mailpit in development (SMTP 1025, web UI 8025).
  • It never reads another service's tables. The words of the emails are written here (EmailTemplates); callers only say what happened.

Important code paths, step by step

A. Booking asks for an email

  1. SecurityConfig chain 1 sends /internal/** through InternalApiKeyFilter: a missing or wrong key gives 401 invalid_api_key.
  2. NotificationController.send validates the body (@Valid); a failure becomes 400 through GlobalExceptionHandler.
  3. NotificationService.accept (one @Transactional transaction): look up dedupe_key; if found, return it with created=false (HTTP 200).
  4. Otherwise EmailTemplates.render builds subject, text and HTML; the base64 attachment is decoded.
  5. EmailRepository.insert stores the row PENDING, attempts 0, next_attempt_at = now. If two requests with the same key race, the unique constraint raises ORA-00001 (DuplicateKeyException) for the loser, which then returns the winner's row (200).
  6. AuditTrail.record adds an audit_log row (actor booking-service, action QUEUE) in the same transaction and logs after commit.
  7. The controller answers 202 { id, status }. Nothing was sent yet.

B. Sending (EmailDispatcher.dispatchDue)

  1. findDueIds: up to 20 PENDING rows with next_attempt_at <= now, oldest first.
  2. For each id, find loads the whole row; SmtpEmailSender.send builds a multipart MIME message and calls the SMTP server. No transaction is open during the call, so a slow server holds no database lock.
  3. Success: markSent runs UPDATE ... WHERE status = 'PENDING'; it changes the row only once, so an email is never counted twice.
  4. Failure: scheduleRetry sets next_attempt_at = now + min(300, 2^(attempts+1)) seconds (2, 4, 8 ... capped at 300) and keeps the error text. After 300 attempts markFailed sets FAILED and an error is logged. One failing email does not block the others.
  5. If the process dies after the SMTP server accepted the message but before markSent, the email is sent twice. This is accepted on purpose (same ticket).

C. The wording (EmailTemplates.render)

  • Ticket: "confirmed, ticket attached"; the payment line is "Total paid", "Paid at counter" or "Complimentary (no charge)" by payment method.
  • Cancellation: a card booking promises the full refund to the card; a counter booking says the refund is handled at the support desk; a complimentary booking says nothing was charged.
  • Refund: "the refund of X for booking R is done".
  • Times use the configured zone; every request value is HTML-escaped in the HTML part.

Tests

Counts by @Test methods: 8 template tests, 12 database tests, 1 Mailpit test. The database tests need NOTIFICATION_TEST_DB_PASSWORD and run on notification_test; without it they show as SKIPPED. They were not run for this documentation step (comments only).

Known limits

  • At-least-once delivery: a crash between the SMTP send and markSent can send an email twice.
  • An invalid base64 attachment is not validated as base64 by Bean Validation; it throws IllegalArgumentException and is answered as 500 internal_error.
  • RequestLogContext removes a userId field and matches /bookings|payments|tickets|refunds/<id> paths that this service does not have; it is the same filter as in the other services. RequestValidationException and AuditTrail.change are not used here.
  • The audit actor is the fixed text booking-service, whoever really called with the key.
  • The backoff exponent is capped at 2^9 = 512 before the 300 s cap, so the wait is 2, 4, 8, 16, 32, 64, 128, 256, then 300 seconds.
  • The email body stored in the database contains the passenger name, address and journey (needed to resend); there is no clean-up of old SENT rows.

8. API Gateway

Purpose

The Gateway is the single entry point of the system. The browser (and nobody else) calls it. It does four jobs:

  1. Checks the login. Every request except /health and the Stripe webhook must carry a Keycloak access token. The Gateway checks the token's signature, issuer and expiry, and reads the realm roles (USER, ADMIN).
  2. Checks the role. Admin routes answer 403 to a normal user, so the request never reaches a service.
  3. Routes. It forwards each call to the service that owns it, with the caller's token (each Spring service checks the token again).
  4. Composes. A few answers need two services. The Gateway asks both and merges the result: trip search, seat map, board detail, ticket PDF/QR.

It also proxies the WebSocket for live seat updates, forwards the Stripe webhook, and ships its own logs and traces to OpenObserve.

The Gateway has no database, no sessions, no login page and never sees a password. The browser talks to Keycloak directly (authorization code flow with PKCE). The Gateway only downloads Keycloak's public keys (JWKS, a list of keys) to verify tokens.

  • Port 8080 (PORT). Node.js 22 and Express 5. No proxy library: forwarding uses Node's built-in fetch.
  • Calls: Train & Schedule (8081), Booking & Seat (8082), Payment (8083, webhook only), Ticket (8084, internal key), Keycloak (keys), OpenObserve.

Authentication and roles (auth.js)

  1. requireAuth reads Authorization: Bearer <jwt>. A missing header gives 401 unauthenticated.
  2. jwtVerify (library jose) checks: signature with the key named by the token's kid (only RS256 is accepted, which blocks alg: none tricks), issuer equal to KEYCLOAK_ISSUER, expiry (5 s clock tolerance). A bad token gives 401 invalid_token.
  3. No audience check on purpose: Keycloak puts aud: account in these tokens and the Gateway is not a Keycloak client.
  4. The keys are cached for 10 minutes; an unknown kid refreshes them at most every 30 s; a hung Keycloak times out after 5 s. If the keys cannot be fetched the answer is 503 auth_unavailable (an outage is not the caller's fault).
  5. The caller becomes req.user = { sub, name, email, roles }; roles come only from realm_access.roles.
  6. requireRole('ADMIN') answers 403 forbidden when the role is missing.

Code paths, step by step

The generic forwarder (proxy.js, forwardTo)

  1. Builds the target URL from the original URL (path and query string) and the service's base URL.
  2. Refuses (400) if the origin differs or the path is outside the allowed prefix.
  3. Copies only the allowed request headers; sends the body only when express.raw produced a non-empty Buffer.
  4. fetch with redirect: 'manual' and a timeout. Relays status, body and Content-Type, Location, WWW-Authenticate.
  5. Timeout gives 504; any other failure gives 502 and a log line with the host only.

Trip search (search.js)

Ask Train & Schedule for /trips. If it is not a 200 with a trips array, relay it as it is. Otherwise ask Booking & Seat for /trips/{id}/availability?from=&to=&view=summary for every trip at the same time (timeout AVAILABILITY_TIMEOUT_MS) and add availability: { seatsLeft, standingLeft }, or null when Booking cannot answer. A Booking outage must not hide the timetable.

Seat map (seatmap.js)

Validates the id, from and to (digits only). Asks Train & Schedule for the layout and Booking & Seat for the availability together. A 4xx from either is relayed, other failures are 502. composeSeatMap gives each seat its state (a seat Booking does not know is BOOKED, never free), each coach its standing places, and adds the journey (stop times), fares, summary, version and the caller's own myHold.

Board detail (board.js)

Same pattern for admins: layout plus Booking's admin board view for the full journey. Seat states are FREE, HELD, TAKEN; a booking reference appears only on TAKEN, the hold expiry only on HELD; an unknown seat is TAKEN. Answer is private, no-store.

Ticket (ticket.js)

  1. Check the id and that INTERNAL_API_KEY is set. 2. Ask Booking GET /bookings/{id} with the caller's token: 404 for someone else's booking.
  2. If that was a 404 and the caller is ADMIN, ask /admin/bookings/{id}. 4. Only CONFIRMED bookings have a ticket (409 otherwise).
  3. Fetch /internal/tickets/{id}/pdf (or /qr) from Ticket with the internal key (the user token is not sent). A 404 there means "not made yet": 409 ticket_not_ready.
  4. Send the bytes with attachment (PDF) and private, no-store. The file name uses only letters, digits, - and _.

WebSocket (wsproxy.js)

Browsers cannot set headers on a WebSocket and the URL must stay out of logs, so the token travels as a subprotocol: new WebSocket(url, ['v12.stomp', 'access_token.<jwt>']). On the HTTP upgrade event the Gateway: accepts only path /ws (404), method GET with Upgrade: websocket (400), and the web app's origin (403, stops cross-site hijacking); reads the token (401 if none); verifies it with authenticate (401, or 503 when the keys are down); opens a TCP connection to Booking & Seat (502 on failure); replays the upgrade request byte for byte; then pipes the two sockets together. Booking & Seat verifies the same token itself. The log line is WebSocket opened with the user id only.

Logging and traces

log.js writes JSON lines (level, service: gateway, msg, fields) and, when OPENOBSERVE_URL and a user are set, queues them (max 2000, oldest dropped) and posts batches of up to 200 every 2 s to the stream gateway; on failure the batch is put back. accesslog.js adds method, path, status, ms, userId (the token's sub), bookingId, tripId and trace_id; never the query string, headers or body. telemetry.js starts the OpenTelemetry SDK (HTTP and fetch instrumentation) so one trace follows a request into the Spring services, and removes query strings from span attributes.

Known limits

  • getJson is copied in seatmap.js, board.js and ticket.js, and the "relay a 4xx, else 502" block is repeated; a shared helper would remove it.
  • A WebSocket token is checked only on the upgrade. A connection stays open after the token expires; Booking & Seat is the second line of defence.
  • No rate limiting and no request size limit other than 1 MB on bodies read with express.raw.
  • /webhooks/payment accepts any body size up to 1 MB and does not check the signature (Payment does).
  • The access log uses req.path of the app level for /health only; other paths are logged in full (without the query string), including ids.
  • Logs wait in memory; if the Gateway stops before a flush, up to 2 s of records are lost.
  • /admin/ping and /me are development helpers kept in production.

9. Frontend (React web app)

Purpose

The web app is what passengers and admins see. It is a single-page application: the browser loads one HTML page and one bundle of JavaScript once, and React draws every screen after that. Moving between screens changes the address (React Router) without a full page load.

It has two jobs and nothing else:

  1. Show what the backend tells it (trips, seat maps, bookings, tickets, admin lists).
  2. Send the user's actions to the Gateway (pick a seat, pay, cancel, edit a station).

It never decides anything that matters. Prices, the 5-minute hold, who wins a seat, refunds and cancellation rules are all decided by the services. The page only displays the answer, so a user who edits the JavaScript in their browser gains nothing.

  • Built with Vite, TypeScript, React, React Router, keycloak-js (login), @stomp/stompjs (live seat updates), @stripe/react-stripe-js (payment form). Plain CSS, no UI library.
  • In Compose it is served by nginx on port 5173 (infra/docker/frontend.Dockerfile). During development vite serves it on the same port.
  • Talks to three places only: the Gateway (all application data and the WebSocket), Keycloak (login, registration, logout, token refresh, in the browser) and Stripe (the card form inside Stripe's iframe).
  • There are no unit tests in the frontend (the end-to-end smoke test in scripts/smoke-test.mjs covers the main flows through the real API).

Routing and guards

App.tsx builds the table. Three levels, each inside the previous one:

  1. Public (inside Layout): /, the five information pages and * (404).
  2. RequireAuth: if Keycloak has no session, it calls login(window.location.href). The user returns to the page they asked for after signing in.
  3. RequireAdmin: needs the realm role ADMIN in the token, otherwise redirects to /account with a notice. Admin pages are drawn inside AdminLayout.

The guards are a convenience. The Gateway verifies the token and the role again on every request (403 for non-admins), so hiding a page here is not security.

Keycloak and tokens

  • Login, registration and logout are redirects to Keycloak's own pages (authorization code flow with PKCE, client web-app). The app has no password code.
  • initKeycloak() runs once (check-sso with silent-check-sso.html), so a reload keeps the user signed in. It is shared as a promise because React StrictMode runs effects twice.
  • Access tokens live about 5 minutes. AuthProvider refreshes in the background (checks every 20 s, renews when under 60 s are left). getFreshToken() also refreshes (if under 30 s are left) right before every Gateway call, so a request never carries an expired token.
  • If the refresh fails the session is over: notifySessionEnded() makes SessionEnded show a dialog with a Sign in button that comes back to the same page.
  • The user object (sub, name, email, roles) is read from the token for display only.

The fetch helper

gatewayRequest(method, path, { body, withToken }) adds Authorization: Bearer <fresh token>, sends JSON, reads the text and tries JSON.parse. It never throws on HTTP errors: it returns { status, body }, and status: 0 means the Gateway could not be reached. readError(result) reads the shared error shape { error: { code, message, details? } } into { code, message, details[] }. Pages branch on code (for example seats_unavailable, hold_expired, trip_departed) and show message. gatewayDownload(path) fetches binary answers (the ticket PDF and QR) with the token, because an <img> or a plain link cannot send a header.

Important flows, step by step

A. Seat map and the 5-minute hold (SeatMapPage.tsx)

  1. The address carries from and to as stop indexes. load() calls GET /trips/{id}/seat-map. The Gateway composes it from Train & Schedule (layout) and Booking & Seat (availability); the answer includes myHold, the user's own hold, and a version counter.
  2. Clicking a free seat calls POST /bookings/pick. The first pick creates the hold (expiresAt = now + 5 min). Later picks join it and never extend it. 409 seats_unavailable means only that pick failed; the seats already held stay held.
  3. Clicking your own seat calls POST /bookings/{id}/release. Releasing the last item ends the hold on the server.
  4. The countdown (countdown.ts) is expiresAt minus the server's clock, corrected by the skew measured when the answer arrived. At 0 the page waits 1.5 s and reloads, because the server's 1-second sweeper has released the hold by then.
  5. connectLive subscribes to the trip topic. applySeatEvent checks the event's version: older is dropped, a gap means a missed event and the whole map is reloaded, a release that does not cover the whole journey also reloads (another hold may remain on part of it). After a reconnect the map is always reloaded.
  6. "Continue to payment" navigates to /bookings/{id}/pay.

B. Payment (PaymentPage.tsx, StripeCheckout.tsx)

  1. GET /bookings/{id} loads the hold; a poll repeats it every 2 s and a WebSocket HOLD_EXPIRED makes it immediate.
  2. Once, POST /bookings/{id}/payment makes the server check the hold and obtain a Stripe PaymentIntent. The answer has the clientSecret and the publishable key.
  3. Stripe's Payment Element draws the card form in its own iframe. Card data goes straight to Stripe and never touches our code or servers.
  4. confirmPayment(..., redirect: 'if_required'). A decline shows a message and keeps the hold, so the user can try again.
  5. Stripe's browser answer is not trusted. The page shows "waiting for confirmation" until the poll sees CONFIRMED (set by the server after Stripe's signed webhook), then replaces itself with the ticket page.
  6. If the booking becomes EXPIRED or ABANDONED, the page goes back to the seat map with a message ("Your 5 minutes ran out...", or "This trip was cancelled.").

C. Cancelling (MyBookingsPage.tsx)

The list comes from GET /bookings (each entry has cancellable, computed by the server). The user presses Cancel booking, a confirmation text explains the full refund, and POST /bookings/{id}/cancel runs. The server re-checks the cutoff (the train has not left the boarding stop) and answers 409 trip_departed otherwise. After any action the list is reloaded.

D. Admin trips board (TripsBoard.tsx, useBoardData.ts)

useBoardData polls GET /admin/board/trips every 5 s (not while the tab is hidden, back-off up to 60 s on errors, old data stays on screen). Rows whose numbers changed flash. A row opens BoardDetailPanel, where the admin can select seats (AdminSeatPicker), issue a counter or complimentary booking (IssueBookingForm), open a taken seat's booking (BookingAdminPanel) or cancel the whole trip.

How the pieces are shared

smoke-test.mjs

Run: docker compose --profile dev up -d --build, then node scripts/smoke-test.mjs [--keep]. Exit code 0 when every check passes, else 1.

Guards

  1. STRIPE_SECRET_KEY must start with sk_test_, else the script throws before doing anything (it pays with Stripe test cards).
  2. GET /health on the Gateway must be 200, else it prints FAIL and exits 1 (is the stack running?).
  3. Everything it creates carries a random 6-hex tag (stations S<tag>A..C, train SM<tag>, route Smoke <tag>), so it never touches demo data.

Flow (each section starts with a --- ... line)

  1. Doors: tokens for the passenger and the admin; no token and a bad token give 401; a passenger on /admin/stations gives 403; the admin 200.
  2. Admin builds a trip: three stations, a train with one SECOND coach, 6 seats, 10 standing places, a route with fares 100 + 130 EGP, a trip 4 days ahead (created means pushed to Booking & Seat).
  3. Search and seat map: the search result (composed by the Gateway) shows 6 seats and 10 standing places left; the seat map is composed.
  4. Journey 1, pay: the first pick starts the hold (201, PENDING_PAYMENT); another user gets 409 on that seat and 404 on the booking; payment creates a PaymentIntent; the script confirms it with pm_card_visa; the signed webhook reaches Payment through the Gateway; the booking becomes CONFIRMED with 230 EGP; the ticket email with the PDF reaches Mailpit; My bookings lists it.
  5. Journey 2, decline: pm_card_chargeDeclined is declined, the booking stays held (FR-P5), a retry on the same PaymentIntent confirms it.
  6. Journey 3, 3D Secure: the intent needs action, nothing is confirmed; deselecting the last seat ends the hold (ABANDONED) and the PaymentIntent is cancelled at Stripe first.
  7. Cancellation: another user's cancel is 404; the owner's is instant, ends REFUNDED with one refund of 23000 piastres and an email; a passenger on the admin cancel route gets 403; the admin finds the booking by reference and cancels with a reason (actor role ADMIN recorded).
  8. Counter and complimentary bookings (no Stripe): exact-email passenger lookup (partial email: 404); issue as COUNTER (a second submit returns the same booking); the board shows the seat TAKEN; the passenger cannot cancel it (cancel_at_desk); the PDF is one page with reference, "Paid at counter", logo and QR; the admin cancel gives MANUAL_REFUND_DUE, then REFUNDED_AT_COUNTER (idempotent); a complimentary booking needs a reason (400 without) and cancels to NOT_APPLICABLE.
  9. Whole-trip cancel: a confirmed booking and an open hold exist; a passenger gets 403; the admin cancels; the trip ends CANCELLED with nothing pending, the booking is refunded, the hold is EXPIRED, the trip leaves the search.
  10. Observability: OpenObserve search shows Gateway logs with booking and user id, the audit line of the cancellation, traces, and no access_token or Bearer text.
  11. Clean-up: unless --keep, it runs demo-data.mjs reset-test-data as a child process.

Helpers: check (PASS/FAIL line and counters), waitFor (poll until truthy, because the stack is asynchronous), stripe (Stripe REST with the test key), mails (Mailpit list), inspectPdf (inflate the PDF streams to count pages and images and read text), ooSearch (OpenObserve SQL search of the last 20 minutes).   3. One trip (Canal 633, in 2 days) is cancelled with the real whole-trip cancel.
  4. Demo bookings per fillFraction (some trips pinned FULL, NEARLY, or a fixed fraction; M001 stays empty). reset-test-data flow

Annotations and keywords (Java, Spring, validation)

  • @AuthenticationPrincipal: asks Spring to pass the logged-in principal (here the decoded Jwt) into a controller method. B/booking/controller/BookingController.java.
  • @Bean: a method whose return value Spring creates once and shares (a clock, an HTTP client, a security chain). B/common/TimeConfig.java (and the *Config classes).
  • @Component: a class Spring creates and injects by itself (no more specific role). B/live/HandshakeAuthentication.java.
  • @Configuration: a class that holds @Bean methods. B/live/WebSocketConfig.java.
  • @ConditionalOnMissingBean: create this bean only if nobody else defined one (lets tests replace it). services/payment/src/main/java/com/trainbooking/payment/stripe/StripeConfig.java.
  • @ConditionalOnProperty: create this bean only if a configuration property has a given value. services/payment/.../stripe/StripeConfig.java.
  • @DecimalMin, @Digits, @Max, @Min, @NotBlank, @NotEmpty, @NotNull, @Pattern, @Size: input validation rules on request fields (money above zero with two decimals, text length, regex, not empty). Checked when the controller parameter has @Valid. B/booking/model/IssueRequest.java.
  • @EnableScheduling: switches on @Scheduled jobs. The *Application class or a config of each service.
  • @EnableWebSecurity: switches on Spring Security's web rules; the SecurityConfig class defines the filter chains. services/payment/.../security/SecurityConfig.java.
  • @EnableWebSocketMessageBroker: switches on STOMP over WebSocket with a message broker. B/live/WebSocketConfig.java.
  • @ExceptionHandler: a method that turns one exception type into an HTTP answer (the shared { error: { code, message } } JSON). B/common/GlobalExceptionHandler.java.
  • @GetMapping, @PostMapping, @PutMapping, @DeleteMapping, @RequestMapping: bind a controller method to an HTTP method and path. B/booking/controller/BookingController.java.
  • @JsonInclude, @JsonProperty: control the JSON field names and whether empty fields are written. The record classes in model/.
  • @Order: the position of a filter chain or filter when there are several. SecurityConfig classes.
  • @Override: marks that a method replaces one from an interface or parent class; the compiler checks it exists.
  • @Repository: marks a class that does database access. B/booking/repository/BookingRepository.java.
  • @RequestHeader, @RequestParam, @PathVariable, @RequestBody: read a value from a header, query string, path segment or JSON body into a method parameter. B/booking/controller/AdminBookingController.java.
  • @RestController: a controller whose return values are written as JSON. Every *Controller.
  • @RestControllerAdvice: a class that applies @ExceptionHandlers to every controller. B/common/GlobalExceptionHandler.java.
  • @Scheduled: run this method repeatedly on a timer. fixedDelay waits a fixed time after the end of the previous run, so runs never overlap. B/booking/service/HoldSweeper.java.
  • @Service: a class holding business logic. B/booking/service/HoldService.java.
  • @SpringBootApplication: the entry class; enables component scanning and auto-configuration. Each *Application.java.
  • @SuppressWarnings: silences a compiler warning on purpose.
  • @Transactional: run the method inside a database transaction (commit on success, roll back on a runtime exception). propagation = MANDATORY means "fail if no transaction is open", used to guarantee that helper code runs inside the caller's transaction. B/booking/service/BookingLocks.java.

  • @Value: inject a configuration property or environment value into a field or constructor parameter. B/board/service/BoardService.java.

Patterns, terms and technologies

  • ABANDONED / EXPIRED / PENDING_PAYMENT / CONFIRMED / CANCELLED: booking statuses. See chapter 1.
  • Access token: the JWT the browser sends to the Gateway. frontend/src/auth/keycloak.ts.
  • Actor: who did an action (the user's or admin's sub); stored as cancelled_by and in the audit log. B/booking/service/CancellationService.java.
  • After commit: see @TransactionalEventListener.
  • All or nothing: one transaction for a whole pick or a whole bulk create; if any part fails, nothing is saved. B/booking/service/HoldService.java.
  • Audit log: table and log line recording every admin action and booking state change. B/audit/AuditTrail.java.
  • Authorization code flow with PKCE: the login method of the browser with Keycloak: the browser gets a one-time code and exchanges it, proving ownership with a secret it generated (PKCE). No password passes through our code. frontend/src/auth/keycloak.ts.
  • Backoff: waiting longer after each failure (2, 4, 8 ... seconds up to a limit) before retrying. B/booking/service/ExpiryService.java (retryLater).
  • Board: the admin page that lists trips with live seat counts. B/board/service/BoardService.java, frontend/src/pages/TripsBoard.tsx.
  • BLOB: Oracle column type for binary data (the PDF). services/ticket/.../ticket/repository/TicketRepository.java.
  • Client secret (Stripe): a one-use string that lets the browser confirm one PaymentIntent. services/payment/.../payment/model/PaymentSession.java.
  • Compose: Docker Compose, the file docker-compose.yml that starts all services.
  • Constraint (primary key, unique, foreign key, check): rules the database enforces itself. services/booking-seat/src/main/resources/db/migration/V1__create_snapshot_and_reservation_tables.sql.
  • Controller / Service / Repository: the three Spring layers: HTTP in and out; rules; SQL.
  • Counter booking / complimentary booking: a booking an admin confirms without Stripe (paid in person, or free). B/booking/service/BookingIssueService.java.
  • CORS / origin: the browser rule about which web address may call which server; the WebSocket also checks the origin. gateway/src/wsproxy.js.
  • Cutoff: the last moment a booking can be cancelled: the departure of the booking's own boarding stop. B/booking/service/CancellationService.java.
  • Dedupe key: a caller-chosen id so the same email request twice creates one email. services/notification/.../NotificationService.java.
  • DTO: data transfer object, a plain class or record for a request or response.
  • Express / middleware: Node.js web framework; middleware are functions run in order for each request. gateway/src/app.js.
  • fixedDelay: see @Scheduled.
  • Flyway migration: a numbered SQL file (V1__...sql) run once in order; never edited afterwards because Flyway checks its checksum. services/*/src/main/resources/db/migration/.
  • Gateway: the Express app on port 8080, the only entry from the browser. gateway/src/app.js.
  • Hold: seats reserved for 5 minutes while the user pays. B/booking/service/HoldService.java.
  • Idempotent: doing it twice has the same result as once. Used for snapshots, tickets, webhooks, issue and cancel.
  • Idempotency key (Stripe): a string that makes Stripe return the same object for a repeated request. services/payment/.../payment/service/PaymentService.java.
  • JdbcClient: Spring's small SQL helper with named parameters (:name); we use it instead of JPA so the SQL stays visible. Every *Repository.
  • JWKS: the list of Keycloak's public keys used to verify token signatures. gateway/src/auth.js.
  • JWT: a signed token that carries the user id (sub), the roles and the expiry. gateway/src/auth.js.
  • Keycloak: the login server. infra/keycloak/.
  • Live update: a seat or hold change pushed over WebSocket. B/live/LiveUpdates.java, frontend/src/live/connectLive.ts.
  • Lock (row lock): SELECT ... FOR UPDATE makes other transactions wait for the row. The fixed order is trip, booking, seats or standing, version. B/booking/service/BookingLocks.java.
  • MDC: per-thread logging context (user id, booking id, trip id) added to each log line. B/common/RequestLogContext.java.
  • MERGE: Oracle's insert-or-update statement (used for the snapshot). B/snapshot/repository/.
  • OpenObserve / OpenTelemetry: where logs and traces are collected; OpenTelemetry is the standard used to send them. infra/docker/entrypoint-java.sh, docker-compose.yml.
  • ORA-00001 / ORA-00060: Oracle errors: duplicate key (read as "seat taken") and deadlock (read as a conflict).
  • Outbox: a table of jobs written in the same transaction as the state change and delivered later by a poller with retries. B/outbox/service/OutboxWriter.java, OutboxDispatcher.java.
  • Payment Element / PaymentIntent: Stripe's embedded card form (in the browser) and Stripe's object for one payment attempt. frontend/src/components/StripeCheckout.tsx, services/payment/.../stripe/StripeApiGateway.java.
  • Payment wins: a payment that succeeded confirms the booking even if the hold has just expired. B/booking/service/PaymentResultService.java.
  • Poller: a @Scheduled job that looks for due work.
  • Port (hexagonal): an interface a service uses to talk to the outside (PaymentPort, TicketPort, NotificationPort), with a client class implementing it; tests use fakes. B/payment/PaymentPort.java.
  • Resource server: a Spring service that accepts and validates JWTs. SecurityConfig classes.
  • Role: USER or ADMIN, a realm role in Keycloak. gateway/src/auth.js (requireRole).
  • Segment: the leg between two consecutive stops; the unit of availability. B/availability/service/SegmentAvailability.java.
  • Sequence / identity column: Oracle ways to generate ids.
  • Snapshot: the immutable copy of a trip (coaches, seats, stops, fares) that Train & Schedule pushes to Booking. B/snapshot/service/, TS/trip/service/TripSnapshotPublisher.java.
  • Standing capacity: places without a seat; counted per coach and per segment in standing_usage. B/availability/service/SegmentAvailability.java.
  • STOMP: a simple messaging protocol on top of WebSocket (subscribe to topics). B/live/WebSocketConfig.java, frontend/src/live/connectLive.ts.
  • Sweeper: the 1-second job that releases expired holds. B/booking/service/HoldSweeper.java, ExpiryService.java.
  • sub: the JWT claim holding the user id; used as a plain value, never a foreign key.
  • Tombstone: a closed payment row without an intent that makes a late create request fail. services/payment/.../payment/service/PaymentService.java.
  • TransactionTemplate: programmatic transactions (run a lambda in a transaction), used when a method must do remote calls outside the transaction. B/booking/service/PaymentStartService.java.
  • Version (per trip): a counter bumped in each hold transaction so the browser can detect missed events. B/live/AvailabilityEvents.java, frontend/src/live/applySeatEvent.ts.
  • Webhook: a request Stripe sends to us when something happens; verified by signature, handled once per event id. services/payment/.../webhook/service/WebhookService.java.
  • WebSocket: a long-lived two-way connection used for live updates.

Frontend terms (React)

  • Component / props / state: a function that returns screen elements; props come from the parent, state is data the component owns. frontend/src/App.tsx.
  • Context: shared data for many components without passing props down (the auth state). frontend/src/auth/AuthContext.tsx.
  • Effect (useEffect): code that runs after render, with a cleanup function that runs on unmount or before the next run (timers, sockets). frontend/src/useBoardData.ts.
  • Guard: a route wrapper that redirects when the user is not signed in or not an admin. frontend/src/auth/guards.tsx.
  • Hook: a function named use... that adds state or effects to a component. frontend/src/useBoardData.ts.
  • Route: a path mapped to a page. frontend/src/App.tsx.
  • Vite: the dev server and build tool. frontend/vite.config.ts.

13. Known issues and improvements

This is a list only. Nothing here was fixed while writing the guide (no behaviour was changed). Items are grouped by where they live. "Observed" items are things noticed while reading the code for chapters 1, 2 and 12; they were not tested.

Train & Schedule (from chapter 3)

  • Duplicate and "in use" errors are recognised by searching the database error text for a constraint name (UK_COACH_POSITION, FK_ROUTE_STOP_STATION ...). Renaming a constraint in a migration would silently turn these 409 answers into 500.
  • TripRepository.findStops uses an IN (:ids) list; Oracle allows at most 1000 values (ORA-01795). A search or admin list returning more than 1000 trips would fail.
  • GET /admin/trips and the admin lists have no paging.
  • TripLayoutService runs one seat query per coach.
  • The push to Booking happens inside the database transaction, so an admin request holds a connection while Booking answers (up to the 5 s read timeout). The rare gap (Booking accepts, then the local commit fails) is documented in TripSnapshotPublisher.
  • A trip's status can be CANCELLED and TripService.update does not check it; Booking refuses the push (trip_not_open), which protects the data.
  • JsonErrorHandlers.handle always says "The ADMIN role is required", also for the internal chain.
  • audit_log.admin_id is 64 characters; the X-Acting-User header is stored as given, so a longer value would make the cancel fail with a 500.

Booking & Seat (from chapter 4)

  • AdminBookingQueryService.toAdminView and BookingQueryService.toView read the trip info and items with separate queries per booking (and two queries per stop): up to 100 bookings in a search and 50 in "My bookings" cost hundreds of small queries.
  • The support search uses UPPER(reference) = :ref, which cannot use the unique index on reference.
  • BookingRepository.findPassengersByEmail knows only users who already have a booking, and excludes the literal user id demo-passenger.
  • The STOMP broker is in memory: with two instances of this service, a client would only get the events of the instance it is connected to.
  • OutboxDispatcher runs jobs one after another in one thread (20 per tick). A slow Ticket or Notification (10 s read timeout) delays every other job.
  • A late-paid hold on a CANCELLING trip is confirmed and then refunded (by the next pass) instead of being refused when the user clicks "Continue to payment".
  • HoldService.pick maps a lock timeout (PessimisticLockingFailureException) to "seats unavailable", which can be a slightly misleading message for a busy database.
  • ExpiryService.retryLater only logs an error from the 5th attempt; a hold whose release keeps failing stays held until someone looks at the log.
  • JsonErrorHandlers.handle always says "The ADMIN role is required.", also if the 403 comes from another rule.
  • V1__create_snapshot_and_reservation_tables.sql still contains a TODO(slice 7) comment that is done (migrations are never edited, because Flyway checks their checksum).
  • Test smell: FakeTicketPort.issue has a redundant !issueCalls.isEmpty() test (it is always true after the add).

Observed while writing chapters 1, 2 and 12

  • Copied code across services. ApiError, GlobalExceptionHandler, RequestLogContext, RequestValidationException, AuditTrail, AuditLogRepository, InternalApiKeyFilter and JsonErrorHandlers exist as near-identical copies in each Spring service (there is no shared library on purpose). A fix in one (for example the fixed 403 text above) must be repeated in all.
  • Polling everywhere. The sweeper, the outboxes, the email dispatcher, the trip-cancellation worker and the board all poll on a timer. This is simple and safe, but adds constant database load and up to one interval of delay; the board in the browser polls every 5 s per open tab.
  • Failure of a one-way chain is only logged. If Booking permanently refuses a Payment message, or an outbox row keeps failing, the main sign is a log line (the booking itself is never changed by a ticket or email failure, by design). There is no admin screen for stuck outbox rows or FAILED emails.
  • Stripe is test mode only by design (StripeKeyGuard refuses live keys); the minimum charge of about US$0.50 makes cheap fares answer 409 amount_too_small.
  • Gateway composes and calls without a circuit breaker. The seat map and the board detail call two services in parallel and fail as a whole if one does not answer; search degrades gracefully (availability: null), the seat map does not.
  • Single-instance assumptions. The in-memory STOMP broker, the Gateway's cached keys and the schedulers (no leader election, jobs rely on row locks and conditional updates) assume one instance of each service.
  • Counter bookings and refunds. A cancelled COUNTER booking only reaches MANUAL_REFUND_DUE; the money is handed back by a person and an admin records it (REFUNDED_AT_COUNTER). There is no reminder for refunds that stay due.
  • A hold that passed its time but was paid at the counter is refused (no "payment wins" for admins), which is by design but can surprise an admin who is slow.
  • Timezone. Booking & Seat and Train & Schedule show stop times in trainbooking.timezone (default Africa/Cairo); a deployment in another zone must set it in every service and the web app shows the clock part as given.
  • Docs. Chapters 5 to 11 and the per-service READMEs were not available when this chapter was written; their known limits must be added below.

Known limits of chapters 5 to 11 (copied from each chapter)

Chapter 10: Infrastructure (10-infrastructure.md)

  • start-dev and KC_HOSTNAME=http://localhost:8180 are for local use only; production would need HTTPS, a real hostname and a different realm file.
  • The comment above stripe-cli in docker-compose.yml still says the Gateway runs on the host; in the current stack it is a container and the CLI forwards to http://gateway:8080/webhooks/payment.
  • The Spring image copies ...-0.0.1-SNAPSHOT.jar, so changing the version in build.gradle breaks the Docker build until the Dockerfile is updated.
  • stripe/stripe-cli:latest and axllent/mailpit:latest are not pinned; the other images are.
  • The OpenTelemetry agent is downloaded at build time without a checksum (the Keycloak drivers have one).
  • The train-schedule timezone variable is TRAINBOOKING_TIMEZONE, the other services use TIMEZONE.
  • The _test schema creation relies on a fresh volume; for an existing volume the schema must be created by hand.
  • entrypoint-java.sh is the only LF file of this group (forced by .gitattributes, because a CRLF shell script fails inside Linux).
  • The root build.gradle comments and nginx.conf comments are not covered by the comments-only checker (it does not know those file types); they were verified by stripping comment lines and comparing.

Chapter 11: Scripts and demo data (11-scripts.md)

  • login is copied in both files (no shared module). The HTML scraping depends on Keycloak's form id kc-form-login.
  • SQL in demo-data.mjs is built from constants and database ids (no user input), not bound parameters.
  • The clean-up called by the smoke test needs Docker and the dev stack; if it fails the smoke test only prints a hint.
  • Observability checks depend on log ingestion delay (up to 45 s of waiting).
  • fillTrip writes booking rows without Payment rows, so these demo bookings have no payment record.
  • seedDemo has a leftover unused nowMin (void nowMin).

Chapter 5: Payment (05-payment.md)

  • RequestValidationException is not thrown anywhere in Payment and GlobalExceptionHandler has no handler for it (copied from the other services).
  • AuditLogRepository Javadoc still says "admin" and CREATE/UPDATE/DELETE; Payment writes CREATE, INTENT, CANCEL, INVALIDATE, RESTART, TOMBSTONE, SUCCEEDED, REQUEST, FAILED.
  • RequestLogContext removes the userId key but Payment never sets it (no user token reaches this service).
  • RefundService.attempt reads the payment with an unlocked findByBooking; safe because a succeeded payment never changes, but it relies on that.
  • A refund stuck in PENDING because Stripe stays in requires_action is only finished by a webhook; there is no polling of Stripe.
  • OutboxRepository.markFailed leaves a refused REFUND_STATUS message without any alert beyond an error log line.

Chapter 6: Ticket (06-ticket.md)

  • QrTokens.verify has no caller yet: there is no gate-scanner endpoint (not in the SRS list of endpoints).
  • The QR token is a bearer secret; the answer of /qr and the PDF contain it, so only trusted services may call these routes (they are internal-only).
  • The PDF is drawn before the INSERT, inside the transaction; a race loser draws a PDF that is thrown away.
  • RequestValidationException and AuditTrail.change are shared code that this service does not use.
  • The audit actor is always booking-service (the real user is not known here), and the column is named admin_id.
  • Only English text; characters outside the Windows-1252 set (Arabic, emoji) are replaced by ? on the PDF.
  • The logo needs a PNG file (OpenPDF cannot draw SVG); without it the PDF has a plain header.

Chapter 7: Notification (07-notification.md)

  • At-least-once delivery: a crash between the SMTP send and markSent can send an email twice.
  • An invalid base64 attachment is not validated as base64 by Bean Validation; it throws IllegalArgumentException and is answered as 500 internal_error.
  • RequestLogContext removes a userId field and matches /bookings|payments|tickets|refunds/<id> paths that this service does not have; it is the same filter as in the other services. RequestValidationException and AuditTrail.change are not used here.
  • The audit actor is the fixed text booking-service, whoever really called with the key.
  • The backoff exponent is capped at 2^9 = 512 before the 300 s cap, so the wait is 2, 4, 8, 16, 32, 64, 128, 256, then 300 seconds.
  • The email body stored in the database contains the passenger name, address and journey (needed to resend); there is no clean-up of old SENT rows.

Chapter 8: Gateway (08-gateway.md)

  • getJson is copied in seatmap.js, board.js and ticket.js, and the "relay a 4xx, else 502" block is repeated; a shared helper would remove it.
  • A WebSocket token is checked only on the upgrade. A connection stays open after the token expires; Booking & Seat is the second line of defence.
  • No rate limiting and no request size limit other than 1 MB on bodies read with express.raw.
  • /webhooks/payment accepts any body size up to 1 MB and does not check the signature (Payment does).
  • The access log uses req.path of the app level for /health only; other paths are logged in full (without the query string), including ids.
  • Logs wait in memory; if the Gateway stops before a flush, up to 2 s of records are lost.
  • /admin/ping and /me are development helpers kept in production.

Chapter 9: Frontend (09-frontend.md)

  • No automated frontend tests; only the smoke test exercises the screens' backend paths.
  • The seat-plan helper planOf is copied in three files (SeatMapPage.tsx, AdminSeatPicker.tsx, BoardDetailPanel.tsx), with slightly different types.
  • Stations.tsx declares its own Station interface instead of using the one in adminTypes.ts.
  • TripsBoard.tsx fixes the railway's time zone to Africa/Cairo in code, while the backend setting is trainbooking.timezone.
  • SearchTrips.tsx disables an ESLint rule (exhaustive-deps) on the hand-over effect on purpose; it must run once when the stations arrive.
  • In MyBookingsPage.tsx the message object has an ok flag that is always false (successes use a toast).
  • EXPIRED_MESSAGE is exported from PaymentPage.tsx and imported by the seat map page, a small cross-page dependency.
  • The hold banner polls GET /bookings every 30 s and on every page change; the payment page polls every 2 s. Both are safety nets next to the WebSocket and cost one request each.
  • A signed-out visitor on the landing page types station names; the names are matched to codes only after sign-in on the search page.
  • The comments in JSX markup were not added inline (a {/* */} adds an empty expression that the comments-only checker cannot tell from code); each component is described by the comment above it instead.
